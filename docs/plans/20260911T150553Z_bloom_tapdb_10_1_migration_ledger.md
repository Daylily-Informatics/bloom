## Data preservation contract

- Preserve stored UID/EUID, prefix, domain, issuer/tenant and creation identities, deleted records, audit history and authoritative lineage.
- Preserve historical prefix/template differences. Never regenerate an existing EUID from its current template.
- Retain BGX identities as assertion/provenance records with duplicate evidence. Add only verified canonical references and lineage; do not invent remote identities.
- Keep unresolved references explicit and deleted history deleted.
- Treat loaded template semantic definitions as immutable. Preserve their UID/EUID, natural coordinates, stored semantic fields, creation identity, audit history and bindings. A semantic change requires a new template version; template-definition migration may change only explicit bookkeeping. This constraint does not prohibit the released schema migration or the separately reviewed Bloom object conversion. Deleted or retired template rows and their bindings remain historical and require no semantic conversion. Add required new template versions without overwriting an existing definition.
- Repair missing native metadata envelopes only through reviewed public APIs. Reject malformed existing values. Archive retired graph metadata only after matching authoritative lineage.
- Do not hard-code observed production counts, paths, prefixes or audit-row expectations in Bloom runtime code.

## Sequence transition contract

- Verify a completed advancement against its prior plan floors. Newly reserved values become future recovery floors and do not trigger repeated advancement.
- The first resumed allocation must exceed stored values, source-next values, reservations and failed-attempt/recovery exposures, including dormant generators.
- Preserve increments, alignment, cache/bounds and ownership. Deduplicate only identical `(name, value, source)` records while retaining original receipts and journals.
- A parser or transport failure never justifies replaying a possibly committed migration. Inspect terminal native receipts and journals, then use native reconciliation for ambiguity.

## Upstream XRF compatibility handoff

TapDB `10.1.1rc1` and `10.1.2` cannot use Bloom's preserved historical core XRF template. Bloom has one active `reference/external_identifier/tapdb_object/1.0` row with prefix `XRF`. Against the `10.1.1rc1` packaged definition, only `name`, `json_addl`, and `json_addl_schema` differ: the historical name is `External Object Reference`, the packaged name is `TapDB Object Reference`, both metadata envelopes have the same top-level keys, and the historical schema is null while the packaged schema is an object. The selected-field hashes are `1327ee6d0638660a5f91734d1efca721f82608a52b12e2ebf2fdc298f89dab55` historical and `319725fef0e110d7605af7b093e6749d16ea55ba8e9158d64778a28554fe2a65` packaged. Protected operator receipt `xrf-template-upstream-gap.json` has SHA-256 `8bf221457964e12a48a85c3a0f1af0b4b650d24b4be6d62645eca6ae9cf99b62`.

The exact public failure path is `external_references._reference_kind` → `_is_exact_xrf_template` → `ExternalReferenceContractError`: the native reader compares the parent template against every packaged core field, including the three historical differences. `seed_templates(overwrite=False)` preserves and skips the existing natural identity, and the migrated natural-identity constraint prevents inserting another exact `1.0` row. Bloom's read-only XRF planner therefore stopped before creating a receipt or mutating the database. A Bloom-only relaxed check would still create references that the public native reader rejects and is prohibited.

The historical template has zero bound instances (active or deleted), zero targeting lineages, and zero native XRF links. The complete public seeding assignment comparison shows only three semantic deltas: `name` (`External Object Reference` versus `TapDB Object Reference`); `json_addl` defaults (`external_identifier`, `foreign_uid`, `href`, `root_euid`, `system` versus `target_object_euid`, `target_object_kind`, `target_service_id`, `target_tenant_id`); and `json_addl_schema` (null versus the canonical object). `polymorphic_discriminator`, domain `M`, prefix `XRF`, instance polymorphic identity, validator `UNIVERSAL_PASS@1`, active status, singleton flag and deletion flag already match. This zero-use result does not permit semantic overwrite under the clarified template contract.

The upstream behavior must preserve the historical template UID, EUID, natural identity, prefix, stored semantic fields, historical bindings, and audit evidence. New canonical XRF semantics require a new template version selected by the public writer and recognized by the public reader; deleted or retired historical versions need no semantic rewrite. The Bloom conversion must then retain all 186 original BGX UID/EUID/deletion/provenance dispositions and prove the representative native reader round trip already required by B03.

This defect invalidated the XRF-specific portion of B03, the `10.1.1rc1` dependency input of B04, and the Bloom `10.0.0` image digest as a deployable acceptance artifact. It did not invalidate the already committed schema receipt, the frozen identity/allocator contract, Bloom application behavior under the old exact input, Kahlo `8.0.0`, sibling images, or the integrity of the recorded build itself. TapDB `10.1.3` now supplies the required additive versioned contract. Bloom adoption requires the exact new pin, focused XRF preservation/native-reader proof, renewed bounded B03 review, one replacement designated broad run and one replacement Bloom patch image/digest. These are the recorded proven-defect exceptions. Atlas remains untouched.
